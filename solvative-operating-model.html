Document scope

This brief governs how Solvative's product teams build, launch, and maintain SaaS products. It covers team structure, development workflow, engineering standards, security and compliance, ISV partner requirements, release management, observability, QA, incident management, support integration, documentation, tooling, metrics, governance, and AI development and operations.

Design principle: Every process in this document exists to prevent a specific class of problem or accelerate a specific class of outcome. If a process cannot be justified on those terms, it is not in this document.

Discovery

Solvative does not solution an architecture, program, or project without Discovery. Discovery is a required phase with defined activities and deliverables, and it precedes any commitment to a solution, a platform, or an estimate. This holds even when delivery is Agile. Discovery is not a waterfall gate and does not mean big design up front; it is a time-boxed inception that establishes enough shared understanding to start safely, followed by continuous, dual-track discovery that runs alongside delivery so learning keeps feeding the backlog.

The rationale is the same design principle that governs the rest of this document: most failures are failures of understanding, the wrong problem, the wrong scope, an unexamined constraint, an unowned system of record, not failures of engineering. Discovery exists to surface those while they are still cheap to fix.

Discovery objectives:

  • Define the problem and the measurable outcome, and name who owns it
  • Align stakeholders on scope, constraints, and success criteria
  • Assess the current state: systems, data, integrations, and organizational reality
  • Shape the solution and architecture enough to estimate and de-risk it
  • Identify risks, dependencies, and the system-of-record decisions
  • Produce a prioritized roadmap and a defensible first increment

Standard Discovery activities:

  • Stakeholder interviews and working sessions
  • Current-state assessment of systems, data, and integrations
  • Requirements and success criteria expressed as measurable outcomes
  • Capability and gap analysis (native versus configure versus build)
  • Architecture and integration shaping, including system-of-record decisions
  • Security, compliance, and risk review appropriate to the domain
  • Estimation, sequencing, and roadmap

Standard Discovery deliverables:

  • Problem statement and measurable target outcomes
  • Stakeholder and persona map
  • Current-state assessment
  • Target solution sketch or architecture-on-a-page, with key decisions captured as ADRs (Section 11) and significant ones run through the RFC process (Section 14)
  • System-of-record and integration inventory
  • Non-functional requirements (scale, performance, availability, security, data)
  • Risk register with owners
  • Prioritized roadmap and a defined first increment
  • A proceed, refine, or stop recommendation

Discovery and the work pipeline. Discovery feeds the intake pipeline in Section 2: its outputs are what move a backlog item from Refined to Ready, and they populate much of the Definition of Ready. Discovery deliverables are inputs to delivery, not documents filed and forgotten.

Discovery in Agile (dual-track). Inception Discovery is time-boxed to the smallest effort that makes starting safe, never an open-ended analysis phase. Thereafter discovery and delivery run as parallel tracks: the team keeps validating assumptions, refining the next increment, and feeding findings back into the backlog. Discovery is continuous, lightweight, and evidence-driven, not a one-time gate that licenses the team to stop learning.

Domain Discovery. Each domain tab (IIoT, B2C, and B2B) carries a Discovery section that specializes this standard with the stakeholders, assessment areas, deliverables, and exit criteria specific to that domain. AI features carry their own Discovery in the AI Addendum.

2. Development workflow

Sprint cadence (2-week sprints)

  • Monday Week 1: Sprint planning (2 hours maximum)
  • Daily: 15-minute async standup via Slack; no synchronous standup unless a blocking issue requires it
  • Wednesday Week 2: Sprint review with stakeholders (1 hour)
  • Friday Week 2: Retrospective (45 minutes) plus next sprint prep

Work intake pipeline

Backlog → Refined → Ready → In Progress → Code Review → QA → Staging → Production

AI-assisted backlog management: Use Jira's AI features for sprint health insights, bottleneck detection, and story point calibration. Supplement with Claude Code or Cowork for requirements synthesis from customer feedback, support ticket themes, and stakeholder notes.

Definition of Ready

  • User story written with clear acceptance criteria
  • Technical approach documented for items above 3 story points
  • Dependencies identified and unblocked
  • Effort estimated by the team
  • Designs approved where UI changes are involved
  • API contracts defined for integration work
  • Prompt/model version specified for AI features

Definition of Done

  • Code reviewed and approved (2+ reviewers; 1 senior minimum)
  • Unit tests written (80%+ coverage for new code; 100% for critical paths)
  • Integration tests passing
  • SAST scan passed (no high or critical findings)
  • Documentation updated: API docs, user docs, runbooks
  • Observability added: structured logs, metrics, traces
  • Deployed to staging and smoke-tested
  • PM acceptance confirmed
  • For AI features: eval suite passing, prompt version committed, cost estimate logged

3. Engineering standards

Code quality gates (automated in CI/CD)

Pre-merge requirements:

  1. Linting and formatting: enforced via pre-commit hooks (ESLint, Prettier, Black, etc.)
  2. Unit tests: 80% coverage minimum; CI fails below threshold
  3. SAST scanning: Semgrep (open source, free tier) or Snyk; blocks on high/critical findings
  4. Dependency scanning: automated CVE checks and license compliance
  5. Code review: 2 approvals required; 1 senior engineer minimum; CodeRabbit AI review on every PR as a first pass (does not replace human review)
  6. Integration tests: all critical user flows must pass
  7. Secrets scanning: Gitleaks (open source) on every commit; blocks on detected secrets

AI-assisted code review

CodeRabbit is integrated into all product repositories as the first reviewer on every pull request. It surfaces issues, suggests improvements, and flags security concerns before human reviewers engage. Engineers treat CodeRabbit findings as a checklist to address, approve, or dismiss with documented rationale, not as a gate they can ignore. Human review remains mandatory.

Branch strategy

main (production) ← release/v1.x.x ← develop ← feature/PROJ-123-description
                                             ← bugfix/PROJ-456-description
                                             ← hotfix/PROJ-789-description (branches from main)
  • main: production-ready code only; protected branch, no direct pushes
  • develop: integration branch; auto-deploys to staging
  • feature branches: short-lived (2–5 days maximum); long-running branches are a smell
  • hotfix branches: branch from main, merge to main and develop

Architecture principles

  1. API-first design: OpenAPI/Swagger spec written before implementation; spec is the contract
  2. Model-layer abstraction: LLM provider never coupled directly to application logic
  3. Multi-tenancy by default: tenant isolation designed in from day one; never retrofitted
  4. Stateless services: horizontal scaling must be achievable without refactoring
  5. Idempotency: all state-changing APIs must be safely retriable
  6. Event-driven where applicable: async communication for decoupling (Cloudflare Queues, RabbitMQ, or AWS SQS)
  7. Feature flags for all new features: no dark code in production; flags enable gradual rollout and instant rollback
  8. Edge-first where latency matters: leverage Cloudflare Workers and Pages for low-latency delivery

4. Security and compliance

SOC 2 Type II

SOC 2 Type II certification is complete. The following controls must be maintained continuously:

  • Access control policies enforced and reviewed quarterly
  • Vendor management program current (annual reviews)
  • Incident response plan tested semi-annually
  • Change management process followed for all production changes
  • Centralized logging with 12-month retention
  • Annual penetration testing completed (third party)
  • Employee security training completed annually
  • Background checks completed for all engineering and ops staff

Annual recertification: assign a compliance owner per product responsible for control evidence collection throughout the year, not just before audit. Use Vanta or Drata to automate evidence collection where possible.

Application security (non-negotiable standards)

  • Authentication: OAuth 2.0 / OIDC only; no custom authentication implementations
  • Authorization: RBAC with least-privilege principle; multi-tenant row-level security
  • Secrets management: Infisical (open source, self-hostable) or Cloudflare Secrets for Workers; never in environment variables committed to source control
  • Encryption at rest: AES-256; encryption in transit: TLS 1.3 minimum
  • API authentication: JWT with rotation capability or scoped API keys
  • Input validation: parameterized queries only; all user input sanitized before use
  • Audit logging: all data access, mutations, and authentication events logged with tenant context
  • Content Security Policy headers on all web surfaces
  • OWASP Top 10 addressed in design review before implementation

Infrastructure security (Cloudflare-native)

Cloudflare provides the following security controls by default across all products. These are not optional add-ons; they are part of the base deployment configuration:

  • WAF rules enabled and tuned per application (Cloudflare WAF)
  • DDoS protection active (Cloudflare DDoS L3/L4/L7)
  • Zero Trust access for internal tooling and production system access (Cloudflare Access); no direct SSH to production
  • Bot management enabled for customer-facing APIs
  • Rate limiting per tenant and per endpoint (Cloudflare Rate Limiting)
  • SSL/TLS termination with HSTS and minimum TLS 1.2 enforced

For workloads running on AWS, GCP, or Azure:

  • Network segmentation: public/private subnet separation
  • Intrusion detection: AWS GuardDuty, Azure Defender, or GCP Security Command Center
  • Automated OS and dependency patching

5. ISV partner approval requirements

Pre-submission technical requirements

Authentication and API behavior

  • OAuth 2.0 with platform-specific flows implemented correctly
  • Credentials never logged, exposed in URLs, or stored insecurely
  • API rate limit handling with exponential backoff and jitter
  • Webhook signature verification implemented
  • Graceful degradation when the platform API is unavailable
  • All API calls use bulk/batch endpoints where available to minimize call volume

Data handling

  • No unnecessary data storage; PII minimized
  • Data retention policies documented and enforced
  • Data deletion on app uninstall implemented and tested
  • Platform data governance rules reviewed and incorporated

Performance

  • User-facing interactions: response under 3 seconds
  • Long-running operations handled asynchronously with status feedback
  • Timeout handling implemented per platform specification

Documentation package (required for all ISV submissions)

  • Architecture diagram showing all data flows
  • OpenAPI/Swagger API documentation
  • Installation guide with screenshots
  • User guide covering primary use cases
  • Admin guide for configuration and management
  • Security whitepaper (required for enterprise listings)
  • Data flow diagram: what data is accessed, stored, transmitted, and deleted
  • Privacy policy and Terms of Service (reviewed by legal)
  • Support contact and escalation path

Marketplace listing requirements

  • App name and logo (platform-specific size requirements; check each platform's style guide)
  • Short description (140 characters) and long description
  • Screenshots (5–8, high resolution, platform-specified dimensions)
  • Demo video (2–3 minutes, hosted on YouTube or Vimeo)
  • Category, tags, pricing information
  • Customer support email and portal URL
  • Case studies or customer references (required for enterprise tiers on most platforms)

6. Release management

Release cadence

  • Standard releases: weekly (Thursdays, deployment window 10am–2pm)
  • Hotfixes: expedited process, any day; requires Engineering Lead approval
  • Major releases: monthly with 2-week beta period; customer communication required

Deployment pipeline

Development → Staging (automated on merge to develop):

Merge to develop → CI pipeline → Unit + integration tests → SAST + dependency scan
→ Build Docker image → Push to registry → Deploy to staging → Smoke tests → Notify team

Staging → Production (controlled release):

Release branch created → Full regression suite → QA signoff → Security scan clean
→ Performance tests → PM approval → Deploy production → Post-deploy monitoring

Deployment strategy by risk level

Risk Level Strategy Rollback Time
Low (config, copy) Direct deploy Immediate
Medium (feature, bugfix) Blue-green deployment < 2 minutes
High (schema change, new service) Canary: 5% → 25% → 50% → 100% < 5 minutes
Critical path change Feature flag rollout Instant (flag off)

Database migration rule: migrations run before code deployment and must be backward compatible with the prior release. Forward-only, never destructive in the same deploy as the code change that depends on them.

Release checklist

  • All tests passing (unit, integration, E2E)
  • SAST scan clean
  • Performance test results within acceptable bounds
  • Database migrations tested in staging with production-scale data sample
  • Runbooks updated for new features
  • Monitoring dashboards updated for new metrics
  • Rollback procedure documented and assigned
  • Customer communications prepared (if user-facing changes)
  • Feature flags configured
  • API versioning verified: no breaking changes without a version bump
  • Support team briefed via Slack summary

Rollback triggers (automated monitoring)

  • Error rate increase > 2% sustained for 5 minutes
  • P95 latency increase > 50% sustained for 5 minutes
  • More than 5 customer-reported critical issues within 30 minutes
  • Security vulnerability discovered post-deploy
  • Data integrity issue detected

Business and SaaS metrics (tracked in Grafana)

  • DAU / MAU and trends
  • Feature adoption rate per tenant
  • API call volume by endpoint and tenant (critical for ISV rate limit compliance)
  • Tenant onboarding completion time
  • Integration sync success rate
  • Webhook delivery success rate
  • Multi-tenant noisy neighbor detection (per-tenant resource consumption anomalies)

AI-specific telemetry (tracked in Langfuse)

Every LLM call logs: model name and version, prompt version, input and output token counts, calculated cost, latency (time to first token, total), feature ID, tenant ID, success or failure, and guardrail trigger flags.

Weekly aggregate review: average tokens per call by feature (detect prompt bloat), cost per user action, P95 latency per AI feature, guardrail trigger rate.

Alerting philosophy

  • Page (PagerDuty or equivalent): actionable, urgent, revenue-impacting (API down, auth service unavailable, data loss)
  • Slack alert: degraded but functional (latency elevated, disk approaching threshold)
  • Dashboard trend: non-urgent, review in weekly metrics meeting
  • On-call rotation: 1-week rotations; maximum 2 overnight interruptions per rotation is the target; violations trigger process review

8. Quality assurance

Testing pyramid

         /\
        /  \     AI Evals (golden datasets, LLM-as-judge, human sampling)
       /----\
      /      \   E2E Tests (5% — critical user journeys)
     /--------\
    /          \ Integration Tests (25% — API contracts, service interactions)
   /------------\
  /              \ Unit Tests (70% — business logic, edge cases, utilities)
 /________________\

Test types, ownership, and AI tooling

Unit tests (engineers, written during development):

  • Qodo (formerly CodiumAI) integrated into VS Code and Claude Code workflow for automated test generation suggestions
  • Fast (< 100ms per test), mocked dependencies, run on every commit
  • Coverage enforced by CI; PRs failing the threshold are blocked

Integration tests (engineers and QA):

  • API contract tests using Bruno (open source Postman alternative) or Hoppscotch
  • Database interaction tests against ephemeral test containers (Testcontainers)
  • Third-party integrations tested against sandbox or test environments
  • Run in CI pipeline on every PR

E2E tests (QA engineers own):

  • Playwright (preferred; open source, fast, cross-browser)
  • Critical user journeys only: login, onboarding, core workflow, payment (where applicable)
  • Momentic used for AI-assisted E2E test generation and maintenance (reduces flakiness from manual selector management)
  • Maximum 30-minute execution time; anything longer indicates scope creep in the suite

Performance tests (DevOps and QA):

  • k6 (open source, CNCF) for load and stress testing
  • Target: handle 2x expected peak load with < 10% latency degradation
  • Run before major releases and any infrastructure changes

Security tests (Security Champion and automation):

  • SAST: Semgrep (open source) on every PR
  • DAST: OWASP ZAP weekly against staging
  • Dependency CVE: Snyk or OWASP Dependency-Check daily
  • Penetration testing: third-party annually

AI evals (Engineering Lead and PM, with QA support):

  • Golden dataset per AI feature (minimum 50 representative examples)
  • Automated evals run in CI on every prompt or model version change
  • Human sampling: PM or domain expert reviews 10–20 outputs monthly per AI feature
  • Promptfoo (open source) for automated eval framework

QA risk tiers

Risk Definition Gate
Low Config change, copy update, minor UI fix Automated tests pass = auto-promote
Medium New feature, API change, integration update QA exploratory check (30 min) plus automated
High Schema change, new service, security-relevant change Full regression plus load test plus manual QA

9. Incident management

Severity levels

Severity Definition Response SLA Examples
SEV 1 Complete outage, data loss, security breach < 15 minutes App down, auth bypass, database corrupted
SEV 2 Major feature broken or significant degradation < 1 hour Payments down, sync failing platform-wide
SEV 3 Minor feature impacted; workaround available < 4 hours Single-tenant issue, reports broken, UI bug in core flow
SEV 4 Cosmetic, low impact Next sprint Typo, minor UI inconsistency

AI-assisted incident response

Rootly or incident.io integrated with Slack for automated incident workflows: channel creation, role assignment, status page updates, and timeline logging. This reduces manual coordination overhead during active incidents. Human incident commander retains decision authority throughout.

Incident process

  1. Detect: monitoring alert, customer report, or internal discovery
  2. Triage: assign SEV level, open incident channel in Slack (automated via Rootly/incident.io), assign incident commander
  3. Communicate: update status page within 15 minutes of SEV 1/2 declaration; notify affected tenants
  4. Investigate: use Grafana dashboards, Rollbar error traces, Grafana Tempo distributed traces; AI-assisted log summarization via Claude Code for large log volumes
  5. Mitigate: fix, rollback, or implement workaround
  6. Resolve: verify resolution, all-clear communication, status page updated
  7. Post-mortem: blameless, within 48 hours for SEV 1–2; action items tracked in Jira

Post-mortem template

  • Summary: what happened, when it started, customer impact, duration
  • Timeline: key events from first signal to resolution
  • Root cause: technical and organizational contributing factors (five whys)
  • What went well: detection time, team communication, tooling that helped
  • What needs improvement: gaps in detection, response, or process
  • Action items: owner, Jira ticket, due date, and whether it prevents recurrence vs. improves detection vs. improves response

12. Tooling stack

Principles

  1. Cloudflare-first: use Cloudflare's edge network, security, and compute as the default layer; bring in AWS/GCP/Azure for workloads that require it
  2. Open source preferred: when capability parity exists, prefer open source to avoid vendor lock-in and reduce cost; exceptions documented with rationale
  3. AI-native where it adds real value: every tooling decision should ask whether an AI-first alternative exists that reduces toil without adding fragility
  4. Consolidate to reduce context switching: fewer tools used deeply beats many tools used poorly

The full tool-by-tool stack, including recommended defaults for development, CI/CD, cloud, security, observability, testing, product, and AI development, is managed as a live decision record on the Tools Checklist tab. That tab is the working surface for confirming each tool, assigning an owner, and recording rationale.

13. Metrics and KPIs

Engineering metrics (reviewed monthly)

Velocity and delivery:

  • Sprint velocity and sprint completion rate (track trends, not absolute numbers)
  • Deployment frequency (target: weekly or more frequent)
  • Lead time: commit to production
  • Change failure rate: percentage of deployments causing incidents

Quality:

  • Defect escape rate: bugs reaching production per sprint
  • MTTR (mean time to recovery) by severity level
  • Test coverage: maintain above 80%
  • Technical debt ratio (SonarQube or equivalent)

Reliability:

  • Uptime percentage per product (target: 99.9%+)
  • Incident count by severity (trend down)
  • MTBF (mean time between failures)

Security:

  • Critical CVE remediation time (target: < 24 hours)
  • Open high/critical SAST findings (target: 0 at release)
  • Pen test findings and remediation velocity

Product metrics (reviewed weekly)

Engagement:

  • DAU / MAU ratio (engagement depth)
  • Feature adoption rate per cohort
  • User retention: D7, D30
  • Onboarding completion rate and time to first value

Growth:

  • New signups and activation rate
  • Conversion rate (trial to paid)
  • Expansion revenue (upsell/cross-sell) and net revenue retention
  • Churn rate (monthly, by cohort)

AI feature metrics:

  • AI feature adoption rate
  • Task completion rate for agentic features
  • User override/rejection rate of AI suggestions (high rate = low quality signal)
  • AI-assisted vs. baseline task completion time
  • Cost per AI-assisted interaction (weekly; alert on unexpected spikes)
  • Guardrail trigger rate (spike = adversarial signal or prompt drift)

15. Continuous improvement

Learning culture

  • Blameless post-mortems: focus on system and process failures, not individuals; psychological safety is a prerequisite for honest post-mortems
  • Brown bag sessions: 30-minute async-first tech talks; monthly; any engineer can present
  • Hack days: quarterly; 1–2 days to explore new technology, address pain points, or prototype ideas; no deliverables required

AI Addendum

Additions and updates for AI-native product development and internal AI operations.

Context

This addendum governs two distinct concerns:

Building AI: standards for developing, shipping, and maintaining standalone and embedded AI features in Solvative's SaaS products.

Using AI: how Claude Code, Claude Cowork, and MCP integrations are used in Solvative's internal engineering and operations workflows.

These require separate governance. Conflating them creates gaps in both.

AI feature discovery

No AI feature is committed to a build without discovery. AI introduces failure modes ordinary feature work does not: data that cannot support the task, a model that demos well and fails in the field, cost that scales past the value, a use case that regulation constrains. Discovery is where those are caught cheaply. This specializes the standard Discovery practice in the Core Operating Model for AI work.

AI discovery objectives and activities:

  • Value and outcome hypothesis: what decision or task improves, by how much, and how it will be measured
  • Feasibility assessment, including a small spike against real data rather than a demo on cherry-picked examples
  • Data readiness: whether data of sufficient quality, coverage, and access exists for the task and for evaluation
  • Risk classification under Section 16.1 (Assistive, Automated, Agentic, Decisional) and EU AI Act classification, which gate the approvals required to proceed
  • Eval design: define the golden dataset and success criteria during discovery (Section 16.5); a feature with no measurable bar is not ready to build
  • Cost model: estimated tokens, model tier, and cost per action weighed against the value (Section 17)
  • Build, buy, or compose: model and approach selection behind the model-layer abstraction (Section 16.2)
  • Human-workflow fit: where the human stays in the loop and how outputs are reviewed or overridden

Exit criteria: a measurable value hypothesis; confirmed data and feasibility; a risk and regulatory classification with the right approvals lined up; a defined eval suite and golden dataset; and a cost estimate within an acceptable range. Absent these, the feature returns to discovery rather than entering the build.

16. AI product development standards

16.1 AI feature classification

Classify every AI feature before development begins. Classification determines tooling, testing rigor, compliance requirements, and approval gates.

Class Description Examples Risk Level
Assistive AI augments human decision; human acts Search, summarization, content suggestions Low
Automated AI acts within bounded rules; human reviews output Report generation, data extraction, classification Medium
Agentic AI acts autonomously across multi-step tasks; human approves checkpoints Workflow automation, integration orchestration High
Decisional AI output directly drives business outcomes Fraud scoring, pricing decisions, compliance routing Critical

Classification must be documented in the ADR for each AI feature. Agentic and Decisional features require Engineering Lead sign-off before development starts and CTO approval before production launch.

16.2 LLM integration architecture

Core principles:

  1. Abstract the model layer: application logic must never couple directly to a specific model API. Use LangChain or LlamaIndex as the abstraction layer. Model selection is a configuration concern, not an architectural one.
  2. API-first, model-agnostic: build against a capability (summarize, classify, extract, generate), not a model name. Swapping models must not require application code changes.
  3. Prompts are code: all production prompts are stored in version control, versioned, reviewed, and tested. Prompt changes go through the same PR process as code changes.
  4. Context management is an engineering concern: token budgets, context window limits, and prompt assembly logic live in version-controlled code. No ad hoc string concatenation in application logic.
  5. Async for all non-trivial LLM calls: anything taking more than 2 seconds must be async with streaming or a background job queue. Never block a user-facing request path on a synchronous LLM call.
  6. Stateless by default: LLM calls are stateless. Conversation history is managed explicitly in the data layer (Redis or PostgreSQL) and injected into context; never rely on session persistence in the model API.

Reference architecture (embedded AI):

User Request
    ↓
API Gateway (Cloudflare Workers: rate limit, auth, tenant context)
    ↓
AI Orchestration Layer (prompt assembly, context injection, tool routing — LangChain/LlamaIndex)
    ↓                           ↓
LLM Provider API         RAG Pipeline (pgvector/Qdrant + retrieval)
    ↓
Response Validation (Guardrails AI: format enforcement, PII detection, content policy)
    ↓

    ↓

16.3 Prompt engineering standards

Requirements:

  • All production prompts stored in version control (dedicated /prompts directory per service)
  • Every prompt has a version identifier; version is logged with every LLM call in Langfuse
  • Prompt changes require a code review with an eval run diff attached to the PR
  • System prompts reviewed by a senior engineer and PM before production deploy
  • No user-controlled input injected directly into system prompt instructions; this is a security boundary, not a suggestion
  • Prompt template standard followed (below)

Prompt template standard:

[SYSTEM]
Role definition and behavioral constraints.
What the model is, what it must never do, what tone it takes.

[CONTEXT]
Tenant-specific or session-specific grounding data injected here.
Clearly delimited from instructions. Treated as data, not as commands.

[TASK]
Single, specific instruction. One objective per prompt.

[CONSTRAINTS]
Output format, length limits, language, scope boundaries.

[OUTPUT FORMAT]
Explicit structure: JSON schema, Markdown template, or plain text specification.

Prompt regression testing: every prompt change requires a Promptfoo eval run comparing results against the current production baseline. Eval diff is attached to the PR. Regressions block merge.

16.4 RAG architecture standards

For any AI feature grounding responses in Solvative or customer data:

  • Vector store isolated per tenant; cross-tenant retrieval is architecturally impossible by design (not just by policy)
  • pgvector used as the default vector store (leverages existing PostgreSQL infrastructure); Qdrant used where query performance requires a dedicated store
  • Chunking strategy documented per document type and tuned against retrieval quality metrics; not set once and forgotten
  • Embedding model pinned and version-locked; re-embedding pipeline triggered automatically on model version change
  • Relevance threshold enforced: retrievals below threshold fall back to a defined behavior (return no result, fall back to general knowledge, or surface a "not found" response); they never silently produce hallucinated answers
  • Hybrid search implemented (vector plus keyword BM25): pure vector retrieval underperforms on exact-match queries; this is not optional for production
  • Metadata filtering enforced at query time for tenant and permission boundaries
  • Data freshness tracked: configurable staleness threshold per data type; stale chunks flagged for re-indexing automatically

16.5 AI evaluation framework (evals)

Evals are to AI features what automated tests are to traditional code. They are not optional and they are not a post-launch cleanup task.

Eval types:

Type Measures When to Run
Functional Does output meet task requirements? Every prompt change, every model version change
Regression Did quality degrade from the prior version? Pre-merge, pre-release
Adversarial Does the system handle malicious or edge-case inputs safely? Pre-release; quarterly red team
Latency and Cost Token usage, response time, cost per call Weekly in staging
Human eval Expert quality rating on sampled outputs Monthly; before major releases

Eval infrastructure requirements:

  • Golden dataset maintained per AI feature: minimum 50 representative inputs with expected outputs or quality rubrics; stored in version control alongside prompts
  • Promptfoo integrated into CI pipeline; eval runs on every prompt or model version change
  • LLM-as-judge scoring used for scalable automated quality assessment (scoring rubric documented and version-controlled alongside the prompt it evaluates)
  • Eval results stored in Langfuse; quality trends tracked over time (not just pass/fail snapshots)
  • Human eval cadence defined and staffed; automated evals alone are insufficient for production launch decisions
  • No AI feature ships to production without a passing eval suite and a documented golden dataset

16.6 Agentic system standards

For any product feature where an AI model takes multi-step autonomous actions:

Design requirements:

  • Minimal footprint: agents request only the permissions needed for the current task; no pre-authorized broad access
  • Human-in-the-loop checkpoints: required at high-risk actions, including file writes to customer data, external API mutations, data deletion, financial operations
  • Action reversibility: prefer reversible actions; irreversible actions require explicit user confirmation; document which agent actions are irreversible
  • Audit trail: every agent action logged with timestamp, action type, input state, output state, model version, prompt version; stored per-tenant
  • Circuit breakers: maximum step count, execution time limit (default: 5 minutes), and cost ceiling enforced; runaway agents are a production incident
  • Graceful failure: agents surface failures to users with context and a clear next step; they do not silently produce wrong outputs, loop indefinitely, or consume unbounded tokens
  • Prompt injection defense: all external data passed to agents (web content, user documents, third-party API responses) is clearly delimited in the prompt and treated as untrusted data; it is never permitted to override system instructions

16.7 AI security requirements

In addition to the application security standards in Section 4, AI features introduce a distinct threat surface that requires specific controls.

Prompt injection:

  • Validate and sanitize all user-provided content before it reaches the model context
  • Clearly delimit trusted instructions from untrusted data in all prompts; use structural separators, not just natural language
  • Validate model outputs for signs of successful injection before acting on them (e.g., unexpected instruction-following behavior from what should be a passive data input)
  • Maintain a test suite of known injection patterns; run before every release

Data leakage:

  • Tenant isolation in context assembly verified in every pre-release security review; cross-tenant data exposure is a SEV 1 incident
  • What context was sent with each LLM call is logged (PII-scrubbed) in Langfuse for audit
  • LLM provider data usage policy documented: training opt-out confirmed, data retention period confirmed, referenced in security whitepaper

Model and supply chain risk:

  • Model versions pinned in production; automatic upgrades to new model versions are prohibited without an eval run
  • All AI libraries and SDKs vetted for security posture on the same standard as any other dependency
  • AI providers documented in vendor management program with data access scope recorded

Output validation:

  • All AI-generated content exposed to users passes through Guardrails AI (or custom validation layer) before rendering
  • Structured outputs (JSON, SQL, code) schema-validated before use
  • PII detection on AI outputs before logging or persisting

16.8 Responsible AI and regulatory compliance

EU AI Act (applies to products with EU customers or deployed in the EU):

Risk Tier Examples Requirements
Unacceptable Social scoring, subliminal manipulation Prohibited
High HR decisions, credit scoring, medical AI Conformity assessment, documentation, human oversight, registration
Limited Chatbots, AI-generated content Transparency disclosure to users
Minimal Spam filters, recommendations No mandatory requirements

Every AI feature must be classified against this taxonomy before shipping to EU customers. Classification documented in the feature's ADR.

Minimum responsible AI standards (all products):

  • Users know when they are interacting with AI; AI-generated content disclosed where material
  • Agentic and Decisional features include human review steps before consequential actions
  • Bias testing completed for any feature making recommendations or classifications affecting users
  • Model card completed per AI feature: model used, training data provenance if fine-tuned, known limitations, intended use scope, out-of-scope uses
  • Opt-out mechanism available where AI affects user outcomes: users can request human review
  • Data minimization: AI features use only data necessary for the task

17. AI observability and cost management

17.1 LLM-specific telemetry

Standard application observability (Section 7) does not cover LLM systems adequately. The following is tracked via Langfuse for every LLM call in production:

  • Model name and version
  • Prompt version identifier
  • Input token count
  • Output token count
  • Total cost (calculated at log time using current pricing)
  • Latency: time to first token and total completion time
  • Feature ID and tenant ID
  • Success or failure status
  • Guardrail trigger flags

Langfuse dashboards surface these as aggregate weekly metrics per feature: average tokens per call, cost per user action, P95 latency, error rate, and guardrail trigger rate.

17.2 Cost management

LLM costs scale with usage in ways that are easy to underestimate. Cost management is an engineering discipline, not a finance concern.

Requirements:

  • Monthly AI cost budget defined per product before launch; reviewed monthly against actual
  • Per-tenant and per-feature cost attribution implemented before launch; you cannot optimize what you cannot measure
  • Cost alert: notify Engineering Lead when daily AI spend exceeds 150% of the daily budget average
  • Model tiering strategy documented and enforced: do not default to the most capable model for every call
  • Semantic caching implemented for high-frequency, low-variability calls (GPTCache or Redis vector similarity)
  • Token budgets enforced in prompt assembly: unbounded context injection is a cost incident waiting to happen

Model selection by use case:

Use Case Tier Rationale
Classification, routing, extraction Smallest capable model High volume, low complexity
Summarization, structured drafting Mid-tier Balance quality and cost
Complex reasoning, agentic tasks Most capable model Quality and reliability justify cost
Real-time UI (autocomplete, suggestions) Fastest available Latency is the constraint, not quality

AI operating model summary

Three failure modes this model is designed to prevent:

1. Treating AI features like regular features: they require evals, cost management, guardrails, and prompt version control that normal feature development does not. 2. Treating internal AI tool usage as ungoverned shadow IT: Claude Code and Cowork create real data handling risks and accountability ambiguity if adoption outpaces governance. Rules defined before an incident are followed; rules defined after one are resented.

3. Confusing a working demo with a shippable product: a demo that impresses in a meeting is not a validated AI feature. Evals, adversarial testing, EU AI Act classification, and responsible AI controls are the bar. They are not optional polish.

The tooling in this model is open source where capability parity exists, Cloudflare-native where the edge provides real advantage, and AI-first where AI demonstrably reduces toil without introducing fragility. Every tool choice is documented with rationale. Tools that stop earning their place are replaced.

Scope: what changes for IIoT and OT

Industrial IoT is not a SaaS application with sensors attached. It spans operational technology (the PLCs, RTUs, SCADA, and sensors that control physical processes) and information technology, across an installed base of long-lived equipment that often cannot be patched or rebooted on demand, over networks that are intermittent, constrained, and expensive, in environments where a security failure can become a safety failure. The data is high-volume time-series that means little until it is contextualized against a physical asset, and the value is realized only when an insight drives a physical action: a work order, a setpoint change, an avoided failure.

Three things follow that have no parallel in the commerce tabs. First, the edge is not a performance optimization; it is a hard requirement, because connectivity is unreliable and a plant cannot stop when the link drops. Second, security and safety are joined: the controls protecting an industrial network also protect people and equipment, and the relevant standards are OT standards, not web standards. Third, the platform market is volatile. Google Cloud IoT Core was retired in 2023, and IBM Watson IoT Platform and Arm's Pelion have shut down or restructured, so designing for portability is a first-order architectural concern rather than a nicety.

This tab records the deltas for delivering IIoT solutions across multiple verticals, whether a single-customer industrial deployment or a multi-tenant IIoT product. Everything in the Core Operating Model and AI Addendum still applies; the multi-tenant isolation, observability, and AI governance standards are especially load-bearing here. Because IIoT engagements turn heavily on the physical and organizational starting conditions, this tab leads with Discovery.

Discovery (IIoT)

IIoT solutions fail far more often from misunderstanding the environment than from writing bad code. Discovery exists to understand the physical installed base, the connectivity, the OT and IT organizational split, the safety and regulatory constraints, and above all the value hypothesis, before any architecture is committed.

Objectives:

  • Establish what measurable operational outcome the solution must produce (uptime, OEE, energy reduction, compliance, quality), and for whom
  • Inventory the physical and digital starting conditions: assets, protocols, networks, existing systems
  • Surface the safety, security, and regulatory constraints that will shape, and sometimes veto, the architecture
  • Identify a pilot site or line and a path to scale

Stakeholders to engage:

  • Operations and plant leadership (the outcome owner)
  • OT and controls engineers (who own the equipment and protocols)
  • Maintenance and reliability engineers (the primary beneficiaries of condition and predictive use cases)
  • IT and OT security (who own the network boundary and will gate the design)
  • Field service and commissioning teams (who will deploy and maintain devices)
  • Data and analytics staff (who will consume and model the data)
  • The business sponsor (who owns the value case and the budget)

Current-state assessment areas:

  • Asset and equipment inventory: makes, models, ages, controllers, and which assets matter to the outcome
  • Protocol and interface audit: Modbus, OPC UA and OPC DA, EtherNet/IP, PROFINET, BACnet, DNP3, MQTT, proprietary, and what each asset can actually expose
  • Connectivity assessment per site: available bandwidth, reliability, cost, power, and physical environment (including hazardous areas)
  • Existing systems: SCADA, DCS, historian (for example OSIsoft or AVEVA PI), MES, EAM/CMMS, ERP, and what data they already hold
  • Network topology and Purdue/ISA-95 level mapping; current IT/OT segmentation and any existing industrial DMZ
  • Security posture: asset visibility, segmentation, remote-access methods, patching reality, and prior assessments
  • Data availability and quality: what is already instrumented, sample rates, gaps, calibration, and trustworthiness
  • Safety systems and constraints: safety-instrumented systems that must not be touched, and change-control rules on the floor
  • Vertical and regulatory constraints: the standards that apply to this industry and geography
  • Site and environmental constraints: temperature, vibration, power, hazardous-area classification

Outputs of Discovery:

  • Asset and protocol inventory, and a connectivity map per site
  • A prioritized set of use-case hypotheses, each tied to a measurable outcome and a rough value estimate
  • A target reference architecture sketch and a draft system-of-record map
  • An integration inventory of the enterprise and operational systems to connect
  • Non-functional requirements: device scale, telemetry volume and rates, latency, offline tolerance, retention, availability
  • A risk register (technical, safety, security, organizational) and a phased roadmap from pilot site to fleet scale

Exit criteria (readiness to move from Discovery to design):

  • A prioritized use case with a measurable, owned outcome
  • A named pilot site or line, with stakeholder commitment
  • The system-of-record map drafted and the integration footprint understood
  • The safety, security, and regulatory constraints documented and accepted as design inputs

Reference architecture: edge to cloud

These principles extend Core Section 3. The layers, from the physical process upward:

  1. Field and OT layer. Sensors, actuators, PLCs, RTUs, and the industrial protocols they speak. This layer is owned by OT and is the most constrained and safety-sensitive.
  2. Edge layer. Gateways and edge compute that translate protocols, buffer and store-and-forward during outages, run latency-sensitive logic and edge analytics, and reduce the volume sent upstream. The edge is mandatory, not optional.
  3. Connectivity layer. The transport from edge to cloud, chosen per site (below).
  4. Ingestion and messaging. A broker-based backbone, commonly MQTT, frequently using Sparkplug B for industrial payloads, or a cloud IoT hub. A Unified Namespace pattern (an event-driven, broker-centered single source of current state) is increasingly the organizing model and deliberately flattens the rigid Purdue data flow; reconcile it with the security model rather than ignoring the tension.
  5. Processing, storage, and contextualization. Stream processing, time-series storage, and the step that turns raw tags into a meaningful asset model. Contextualize early; uncontextualized tags are nearly worthless downstream.
  6. Analytics, ML, and applications. Dashboards, condition monitoring, predictive models, digital twins, and the integrations that turn insight into action.

Architecture principles:

  • Edge-first. Process where the data is; send upstream what matters. This serves latency, bandwidth, cost, and resilience at once.
  • Offline-first. Store-and-forward is a baseline requirement; the system must lose no critical data and behave correctly across outages.
  • Contextualize early. Bind signals to a consistent asset model (ISA-95 equipment model is the usual reference) close to the source.
  • Decouple through an event backbone. A broker or Unified Namespace lets producers and consumers evolve independently and lets channels and analytics subscribe without point-to-point coupling.
  • Design for device scale. Thousands to millions of devices change provisioning, updates, and observability from tasks into systems.
  • Design for portability. Given the platform graveyard, keep the data backbone (broker, time-series store, asset model) on portable or open foundations and treat specific clouds as replaceable destinations, not the architecture's center of gravity.

Connectivity and edge design

Connectivity is a per-site engineering decision with cost and reliability consequences, not a default.

  • Connectivity chosen per site against bandwidth, power, coverage, and cost: wired, Wi-Fi, cellular (4G/5G, LTE-M, NB-IoT), LoRaWAN, satellite, or private 5G
  • Offline-first and store-and-forward designed in, with defined behavior and data-integrity guarantees across outages
  • Bandwidth and data-cost budget set, particularly for cellular and satellite, where egress and per-message costs accumulate fast
  • Edge protocol support confirmed for the site's equipment (Modbus, OPC UA, EtherNet/IP, PROFINET, BACnet, DNP3, MQTT)
  • Edge compute scoped for latency-sensitive logic and for upstream-volume reduction (filtering, aggregation, edge inference)
  • Edge resilience and remote management: edge nodes are themselves managed, monitored, and recoverable
  • Time synchronization addressed, since time-series data is only as good as its timestamps

Device and fleet management

At fleet scale, device operations are systems, not manual tasks.

  • Provisioning and onboarding, ideally zero-touch, with a defined field workflow for installs and replacements
  • Strong device identity (X.509 certificates backed by a secure element or TPM where available) and mutual TLS
  • Device twin or shadow for desired-versus-reported state
  • Configuration management as code, versioned and auditable
  • Over-the-air firmware updates that are signed, staged, monitored, and rollback-capable; a bad update across a fleet is an incident
  • Full lifecycle handling from commission to operate to secure decommission
  • Fleet observability (connectivity, signal, battery, health) as the operational analogue of the Core Section 7 observability standard, alerting on fleet degradation, not only backend metrics

Data architecture and analytics

  1. Time-series at scale, tiered deliberately. Hot, warm, and cold tiers with downsampling and retention policies set against the use case and cost, not left to default.
  2. Contextualization and asset model. A consistent model (ISA-95 equipment hierarchy) binds signals to assets so analysis and ML have meaning. This is the difference between a data swamp and a usable foundation.
  3. Digital twin where it earns its place. A model of the asset and its state that supports monitoring, simulation, and prediction; scoped to a real use case, not built for its own sake.
  4. Analytics use cases. Condition monitoring, anomaly detection, predictive maintenance, OEE, computer-vision quality inspection, and energy optimization are the common value drivers; pick by Discovery outcome, not by what is fashionable.
  5. Edge-versus-cloud analytics split decided explicitly. Latency-sensitive or bandwidth-reducing inference at the edge; heavy training and cross-fleet analytics in the cloud.
  6. Data quality is an engineering concern. Sensor drift, gaps, and calibration are tracked and handled; a model fed bad signals produces confident wrong answers.
  7. AI and ML follow the AI Addendum, with a critical escalation. Any model whose output can actuate physical equipment or change a setpoint is, by the Section 16 taxonomy, Decisional or Agentic class: it requires hard guardrails, human approval before action, circuit breakers, and reversibility analysis. A wrong prediction that closes a valve or stops a line is a safety event, not a bad recommendation. Predictive models also require drift monitoring and periodic retraining, governed by evals and golden datasets.

OT security and safety

This extends Core Section 4 and is where IIoT diverges most from every other domain in this brief. Security and safety are inseparable here.

  1. Adopt the recognized OT frameworks, not web-security habits. IEC 62443 (jointly ANSI/ISA-62443) is the implementation framework, built on Security Levels and the zone-and-conduit model. NIST SP 800-82 Revision 3 (published September 2023) is the guidance layer and maps to the NIST Cybersecurity Framework 2.0. Where the vertical demands it, NERC CIP (energy) and medical-device regulation apply.
  2. Segment along the Purdue / ISA-95 model and defend the IT/OT boundary. Map assets to levels 0 through 5, place an industrial DMZ at Level 3.5, and ensure no routable path lets the enterprise network reach process control directly. The lesson of major incidents is that the IT/OT boundary is where attacks cross.
  3. Zones and conduits, default-deny. Group assets into zones by shared security requirement; every conduit between zones is explicitly permitted, specific, and monitored. Use data diodes for one-way flows where the criticality warrants.
  4. Secure remote access, never direct. Vendor and engineer access goes through jump hosts and privileged access management, time-bound and audited. No engineering workstation has open internet access.
  5. Asset visibility and passive monitoring. Maintain an OT asset inventory and monitor the network, but note that active scanning can disrupt live industrial systems; prefer passive discovery, per NIST 800-82 guidance.
  6. Treat the patch reality honestly. You cannot patch a running line or reboot a safety system mid-shift. Where devices cannot be patched, compensate with segmentation, allowlisting, and monitoring, and record the exception in the risk register.
  7. Account for insecure legacy protocols. Modbus, DNP3, and OPC DA were designed for reliability, not security. Where you cannot upgrade to secured variants (OPC UA, DNP3 with Secure Authentication), compensate with network controls.
  8. Harden devices and identities. Change default credentials, disable unused services and ports, and give devices real identities.
  9. Safety is paramount and separate. Security controls must never compromise safety-instrumented systems; functional-safety obligations (for example IEC 61508 and 61511, with their SIL levels) take precedence, and any IIoT write-back to equipment is gated by safety review.

Platform selection (IIoT)

There is no universal IIoT platform, and platform longevity is a genuine risk in this market. Record the choice as a Level 3 decision, and weight portability heavily.

Categories and current examples:

  • Hyperscaler IoT: AWS IoT (Core, Greengrass for edge, SiteWise for industrial data) and Azure IoT (IoT Hub, IoT Edge, Azure Digital Twins) are the two full-range survivors. Google retired Cloud IoT Core in 2023; Google Cloud remains strong as a data and analytics destination (BigQuery, Pub/Sub, Vertex AI) reached through a partner gateway rather than a native device layer.
  • Industrial IoT platforms: PTC ThingWorx, Siemens Insights Hub (formerly MindSphere), AVEVA, Inductive Automation's Ignition (widely used for SCADA and IIoT), and edge-focused options such as Litmus Edge.
  • Open source and composable: ThingsBoard (IoT application platform); EMQX and Mosquitto (MQTT brokers, open source); HiveMQ; Node-RED; the Eclipse IoT ecosystem (Ditto for digital twins, Hono, Kura and Kapua for edge); and the InfluxDB or TimescaleDB plus Telegraf plus Grafana stack, which aligns with the observability tooling already in the core model. Apache Kafka or Pulsar for high-volume streaming; Apache IoTDB for time-series.

Selection axes specific to IIoT:

  • Protocol coverage for the actual equipment in scope
  • Edge capability and offline behavior, not just cloud features
  • Device scale the platform genuinely supports
  • Vertical fit and any required certifications (hazardous-area, medical, grid)
  • Deployment model: cloud, on-premises, or hybrid, driven by data sovereignty and OT constraints
  • Security posture and alignment with IEC 62443
  • Vendor longevity and exit cost, weighted heavily given the retirements in this market

Architect's recommendation: do not bet the whole solution on a single proprietary platform's lifecycle. Keep the durable core (the messaging backbone, the time-series store, and the asset model) on portable or open foundations, and treat specific clouds and platforms as replaceable layers above it. This is the same open-source-preferred and lock-in-aware stance as the core model, applied to a market that has repeatedly proven the point.

Domain extension · B2C Commerce

Scope: what changes for B2C commerce

In B2C commerce the storefront is the product. There is no sales engineer to compensate for a confusing flow, no signed contract that survives a bad week of uptime, and no switching cost holding a shopper in place. A customer who waits too long for a page, hits a broken filter, or stalls at checkout simply leaves, and the cost is immediate and measurable in lost revenue, not a delayed renewal.

That changes three things relative to the core model. First, performance and availability are revenue, not hygiene, and they are judged on real consumer devices and networks, not the team's laptops. Second, traffic is spiky and partly adversarial: demand arrives in flash-sale and seasonal peaks, and bots, scrapers, and card-testing rings treat the storefront as an attack surface. Third, the regulatory surface widens to payment-page script integrity and consumer accessibility law, both of which now carry hard, already-passed deadlines.

This tab records only the deltas. Everything in the Core Operating Model and AI Addendum still applies. Where a section below extends or overrides a core section, it says so. Where it is silent, the core standard governs.

Discovery (B2C)

Run Discovery before committing to a platform, a replatform, or a performance and accessibility baseline. The storefront's commercial outcome and its technical constraints are set here.

Objectives:

  • Define the commercial outcome (conversion, revenue, channel growth) and who owns it
  • Assess the current storefront, platform, catalog, and martech reality
  • Establish the performance, accessibility, and SEO baseline and targets
  • Decide platform fit and the channel mix

Stakeholders to engage:

  • Commerce and marketing leadership (the outcome owner)
  • Merchandising and brand (catalog, content, promotions)
  • Performance, SEO, and accessibility owners
  • Payments and finance (PSPs, tax, fraud exposure)
  • IT and the data and analytics team
  • The business sponsor

Current-state assessment areas:

  • Existing storefront and platform, and the reasons behind any replatform
  • Catalog size and quality, and the product information source of truth
  • Search and merchandising maturity
  • Payments: PSPs, methods, tax, and fraud exposure
  • Analytics and martech stack, and the third-party script and tag burden
  • Core Web Vitals baseline on field data, and the performance-budget reality
  • Accessibility audit against WCAG 2.2 AA, and the legal exposure by market
  • SEO and organic baseline, rendering strategy, and information architecture
  • Channels and marketplaces, and internationalization needs

Outputs:

  • Platform fit assessment and capability gap analysis
  • Performance and accessibility baselines and target budgets
  • Customer journey map across the relevant channels
  • Non-functional requirements and a prioritized roadmap with a first increment

Exit criteria:

  • A measurable commercial outcome with an owner
  • A platform decision or a real evaluation shortlist
  • Performance and accessibility baselines captured and targets agreed
  • A prioritized roadmap with a defined first increment

Commerce architecture principles

These extend Section 3 of the core model. The API-first, multi-tenant, stateless, idempotent, and feature-flag principles all carry over without exception.

  1. Decide headless vs. monolith deliberately, per engagement. Composable / headless (MACH-style) buys independent scaling of the storefront, freedom of front-end framework, and best-of-breed services, at the cost of integration and operational complexity. A platform monolith (for example a hosted SaaS commerce platform) buys speed and lower operating burden at the cost of flexibility. Default to the simplest architecture that meets the catalog size, traffic profile, and customization requirements. Document the choice in an ADR.
  2. The storefront is edge-first. Render and cache at the edge (Cloudflare Pages and Workers, Cloudflare Cache and R2) so the common path, category and product pages, is served close to the user. Use static generation or incremental regeneration for catalog pages; reserve dynamic server rendering for personalized or stateful surfaces. This is a direct application of the core "edge-first where latency matters" principle.
  3. Cart and checkout are an isolated, resilient service. They must degrade independently of catalog, search, and recommendations. A failing recommendation widget must never be able to block a purchase. Order capture is idempotent (core Section 3, principle 5) so a retried submission never double-charges or double-orders.
  4. Abstract the payment provider. Application logic talks to a payment capability (authorize, capture, refund, tokenize), never to a single PSP's SDK directly. This mirrors the core model's model-layer abstraction for LLMs and makes adding a provider, or failing over between providers, a configuration change rather than a refactor.
  5. Inventory is a source of truth with explicit consistency rules. Define how oversell is prevented under concurrency (reservations, holds, or compensating actions) before the first sale, not after the first oversell incident. State whether the storefront reads inventory eventually-consistent or strongly-consistent, and design the customer messaging for each case.
  6. Third-party scripts are a governed dependency, not a marketing free-for-all. Every tag, pixel, and widget added to the storefront is a performance cost, a privacy obligation, and, on payment pages, a PCI control (see Security below). Route them through a controlled tag layer and gate additions through engineering review.
  7. Separate the systems of record. Catalog/PIM, orders/OMS, customer/identity, and content/CMS are distinct concerns with distinct lifecycles. Resist collapsing them into one store because a single platform happens to offer all four; couple them through clear contracts.

Storefront performance and peak-event readiness

Performance is a budget that is enforced in CI, the same way coverage and SAST are enforced in the core model.

Core Web Vitals targets (field data, 75th percentile of real users):

Metric Good threshold Notes
Largest Contentful Paint (LCP) under 2.5 s Loading. Hero imagery and above-the-fold product media are the usual offenders.
Interaction to Next Paint (INP) under 200 ms Responsiveness. Replaced First Input Delay in March 2024. Concentrated on JavaScript-heavy filters, search, and checkout.
Cumulative Layout Shift (CLS) under 0.1 Visual stability. Reserve space for images, ads, and dynamically injected content.

Google evaluates these at the 75th percentile of real-user (field) data, so the bar is the experience of a mid-range phone on a patchy connection, not a developer laptop. Pass all three or the page does not pass.

Performance budget (enforced in CI, fail the build on regression):

  • LCP, INP, CLS budgets set per page template and monitored on field data, not just lab data
  • JavaScript shipped to the storefront has a hard size budget per route; new dependencies require justification
  • Images served responsively and in modern formats (Cloudflare Image Resizing or equivalent); never ship a desktop hero to a phone
  • Third-party script weight budgeted and reviewed; tags that breach the budget are removed or deferred
  • Time to first byte protected by edge caching of catalog pages

Peak-event readiness. B2C demand is not uniform. Flash sales, product drops, and seasonal peaks (the November sale period being the obvious one) arrive as multiples of baseline traffic, often 10x or more for a brief window. Treat every named peak as a planned engineering event.

  • Capacity target defined as an explicit multiple of forecast peak baseline, agreed with the business, and load-tested to that target with k6 before the event
  • A game day rehearsal run against staging at peak-scale data and traffic, with the on-call team participating
  • Queue or waiting-room strategy in place for events that exceed safe capacity (Cloudflare Waiting Room or equivalent), so the site degrades into a fair queue rather than a crash
  • Graceful degradation defined per feature: recommendations, reviews, and personalization shed load first; browse and checkout are protected last
  • Inventory oversell protection verified under concurrent load, not just functionally
  • Bot and rate-limit posture tuned for the event (Cloudflare Bot Management and Rate Limiting), with particular attention to inventory-hoarding and checkout-abuse patterns
  • A code freeze window and a named rollback owner for the duration of the event
  • Real-time business dashboards (orders/min, conversion, payment success rate) on screen during the event, not only system metrics

Catalog, search, and merchandising

Discovery is where most catalog revenue is won or lost, and it is largely invisible in standard application metrics.

  1. Treat product data as a managed asset. A product information layer (PIM, or a disciplined catalog service) owns canonical product data, variants, media, and attributes. Downstream surfaces (storefront, search index, marketplaces, ads feeds) are projections of it, kept in sync by an explicit pipeline.
  2. Search is a first-class service, not a database query. Use a dedicated search engine (Typesense or Meilisearch where the open-source preference applies, or a managed service such as Algolia where relevance tooling and operational simplicity justify it). Typo tolerance, synonyms, faceting, and relevance tuning are merchandising controls, not one-time configuration.
  3. Instrument zero-result and low-result searches. A query that returns nothing is a direct demand signal and a direct revenue leak. Track it, surface it to merchandising, and close the loop.
  4. Merchandising controls belong to the merchant. Ranking rules, pinned products, promotional boosts, and category curation are commercial levers. Engineering's job is to make them safe and observable, not to be a ticket queue for every promotion.
  5. AI where it earns its place (per the AI Addendum). Semantic search, query understanding, and recommendation ranking are strong candidates. They are subject to the same eval, cost, and guardrail requirements as any AI feature in Section 16: a golden dataset of representative queries, relevance evals on every change, and a defined fallback when confidence is low.

Checkout, payments, and fraud

This section extends core Section 4. The core PCI posture, use Stripe or Braintree, never store card data, reduce scope, still holds and is the foundation here.

Checkout integrity:

  • Order capture is idempotent and safely retriable; a network retry never creates a duplicate order or charge
  • Cart and checkout are resilient to failures in non-essential services (recommendations, reviews, loyalty)
  • Inventory is validated at the point of capture, with clear customer messaging on the oversell edge case
  • Guest checkout supported; forced account creation is a measurable conversion tax
  • Address, tax, and shipping calculation handled server-side and validated; never trusted from the client

Payments:

  • Payment provider abstracted behind an internal capability interface (see architecture principle 4)
  • Card data tokenized via the PSP using hosted fields or an equivalent so card data never touches Solvative systems, keeping PCI scope minimal
  • Strong Customer Authentication / 3-D Secure supported where the market requires it
  • Relevant alternative payment methods supported per market (digital wallets, and buy-now-pay-later where the business requires it)
  • Tax calculation via a dedicated service (for example Avalara or equivalent) where jurisdictions warrant it
  • Payment reconciliation and refund flows designed and tested, not assumed

PCI DSS payment-page script controls (now mandatory). PCI DSS v4.0.1 is the current standard, and its e-commerce client-side requirements moved from best practice to mandatory on 31 March 2025. They target e-skimming (Magecart-style) attacks and apply to any merchant whose pages can affect the payment transaction.

  • Requirement 6.4.3: maintain an inventory of every script loaded on payment pages, with a written justification for each, a method to authorize each script, and a method to assure each script's integrity
  • Requirement 11.6.1: a tamper- and change-detection mechanism that alerts on unauthorized modification of payment-page content and HTTP headers as received by the consumer's browser
  • Minimize the number of scripts on payment pages to shrink the attack surface; this is the cheapest control available
  • Where a PSP iframe is embedded, confirm the PSP's own compliance and keep the hosting page's scripts inventoried

Fraud:

  • Fraud screening on orders (PSP-native tooling, or a dedicated service such as Signifyd or Riskified where chargeback exposure justifies it)
  • Card-testing defenses on the payment endpoint (rate limiting, velocity checks, bot management)
  • Chargeback and dispute handling defined as an operational process, with the rate tracked as a KPI

Security, compliance, and data handling

Extends core Section 4. In addition to the standard application and infrastructure security controls:

Consumer privacy and consent. B2C means large volumes of consumer personal data and marketing activity, which raises the GDPR and CCPA/CPRA stakes from core Section 4.

  • Consent management platform in place for cookies and tracking, with consent captured before non-essential tags fire
  • Server-side tagging preferred over client-side where feasible, to reduce data leakage, improve performance, and keep the payment-page script surface small
  • Right to deletion and data export implemented and tested across all consumer data stores, including the marketing and analytics layer
  • Data minimization in marketing flows: collect and retain only what the campaign actually needs

Accessibility is now a legal requirement, not a nicety. Target WCAG 2.2 Level AA, the current guideline version and the de facto standard referenced by courts and procurement.

  • Storefront, search, filters, cart, and the full checkout flow tested against WCAG 2.2 AA with assistive technology, not only automated scanners (automated tools catch roughly a third of issues)
  • Keyboard-only navigation works end to end, including multi-step checkout and dynamic filters
  • Accessibility checks integrated into CI and into the Definition of Done for any UI change
  • For EU customers: the European Accessibility Act has been enforceable since 28 June 2025 and applies to any business serving EU consumers regardless of where it is headquartered, with limited exemption only for microenterprises; conformance is demonstrated via EN 301 549 (WCAG 2.1 AA baseline, 2.2 as best practice) plus a published accessibility statement
  • For US customers: ADA Title III is applied to commercial sites, with WCAG AA as the de facto bar; overlay widgets do not provide compliance or legal protection
  • Accessibility conformance evidence maintained year-round by the named owner (mirrors the compliance-owner model in core Section 4)

SEO, content, and internationalization

For most B2C catalogs, organic search is a primary, compounding acquisition channel, which makes rendering and information-architecture decisions commercial decisions.

  1. Rendering strategy is an SEO decision. Catalog and content pages must be crawlable and fast: prefer server-rendered or statically generated HTML with real content in the initial response, not content that only appears after client-side JavaScript executes. Core Web Vitals are a ranking input, so the performance budget above is also an SEO control.
  2. Structured data everywhere it applies. Product, offer, breadcrumb, and review schema (schema.org) so listings are eligible for rich results.
  3. Own the URL and redirect lifecycle. Stable, semantic URLs; managed redirects on catalog changes; no orphaned or duplicated product URLs bleeding ranking signals.
  4. Internationalization is structural, not a translation layer bolted on late. Locale, currency, tax, address formats, and hreflang are designed in. Content modeling in the CMS or DXP supports localized variants without forking the codebase.
  5. Content and commerce are integrated. Editorial content (guides, lookbooks, landing pages) and commerce share a navigation and search surface; a headless CMS keeps content authorable without engineering involvement.

Conversion, experimentation, and personalization

Conversion optimization is a standing discipline with its own infrastructure and guardrails, not an occasional project.

  1. Experimentation is first-class and safe. A feature-flag and experimentation layer (core Section 3 already mandates flags) supports controlled A/B and multivariate tests. Every experiment declares guardrail metrics (checkout completion, payment success, error rate) that automatically stop a test that harms revenue. No experiment touches the payment path without explicit review.
  2. Analytics is dual-layer. Client analytics (for example GA4) for behavior, plus server-side event capture for accuracy and resilience against client-side blocking. Define the canonical conversion events once and emit them consistently.
  3. Customer data is unified through a CDP. A customer data platform (RudderStack where the open-source preference applies, or a managed equivalent) provides a consistent customer profile across analytics, marketing, and personalization, with consent state attached.
  4. Personalization and recommendations follow the AI Addendum. Recommendation and personalization models are AI features under Section 16: classified by risk, backed by evals, cost-managed, and guardrailed. A recommender that degrades must fail closed to a sensible non-personalized default, never to a broken widget that blocks the page.
  5. Lifecycle messaging is owned and measured. Cart abandonment, post-purchase, and win-back flows run through the transactional and marketing comms stack (core lists Customer.io for transactional comms), with deliverability and unsubscribe handling treated as first-class.

Platform selection and channel requirements

There is no single correct commerce platform; there is a correct platform for a given catalog size, customization need, team, and budget. Select deliberately and record the decision as a Level 2 or Level 3 decision per the core governance framework.

Selection axes:

  • Hosted SaaS platform (for example Shopify / Shopify Plus, BigCommerce): fastest time to market, lowest operating burden, strong ecosystem, less architectural freedom. Strong default for standard catalogs and lean teams.
  • Composable / headless (for example commercetools, or a headless storefront over a commerce API): maximum flexibility and independent scaling, highest integration and operational cost. Justified by genuine customization or scale requirements.
  • Open-source platform (for example Medusa, Saleor, Vendure, or Sylius/Spree): full control and no licensing lock-in, consistent with the core open-source preference, in exchange for owning hosting, security, and upgrades. Justified when control and cost structure matter and the team can own the operational burden.
  • Enterprise suite (for example Adobe Commerce, Salesforce Commerce Cloud): deep built-in feature breadth for large or complex B2C operations, at correspondingly higher cost and complexity.

Selection checklist:

  • Total cost of ownership modeled over three years, including platform fees, transaction fees, app/extension costs, and the engineering cost to operate
  • Catalog scale, peak traffic profile, and required customizations mapped against the platform's real limits, not its marketing
  • Exit cost and data portability assessed before commitment; vendor lock-in named explicitly
  • Extension and app ecosystem reviewed for the specific integrations the business needs

Channels and marketplaces. Where the business sells beyond its own storefront:

  • Product feed pipeline to advertising and shopping channels (for example Google Shopping, Meta) kept in sync from the canonical catalog
  • Marketplace integrations (where relevant) treated as ISV-style integrations under core Section 5: rate-limit handling, webhook verification, graceful degradation, and the platform's data and listing rules all apply
  • Partner program certifications maintained where the platform requires them (for example a platform's Plus/partner certification), with renewals tracked like the ISV certifications in core Section 5

Domain extension · B2B Commerce

Scope: what changes for enterprise B2B commerce

In enterprise B2B, the web storefront is one channel, not the whole business. The same account buys through self-service online, through a sales rep who quotes and orders on their behalf, through their own procurement system via punchout, and through EDI, often in the same week. The buyer is an organization, not a person: purchases route through requisitioners, approvers, budgets, and contracts. And the commerce platform is usually not the system of record. Pricing, inventory, and orders typically live in an ERP; accounts, opportunities, and cases live in a CRM. Commerce orchestrates an experience across those systems and the people who operate them.

That reorders the priorities from B2C. Latency and conversion still matter, and the storefront mechanics in the B2C Commerce tab (Core Web Vitals, accessibility, SEO, edge delivery) still apply to any buyer-facing surface, so this tab does not repeat them. But the dominant risks here are correctness and trust: showing a customer the wrong contract price, exposing one account's pricing or catalog to another, dropping an order between commerce and the ERP, or letting an assisted action happen without an audit trail. Those failures lose accounts and breach contracts, not just sessions.

This tab records the deltas for a solution that serves enterprise buyers through blended self-service and assisted selling. Everything in the Core Operating Model and AI Addendum still applies, and the B2C tab governs shared storefront concerns. The sections below are written to be worked through with a business-analyst team: personas and journeys first, then the domain and integration model, then the standard delivery deltas.

Discovery (B2B)

In enterprise B2B, the platform and integration decisions dominate cost and timeline, and both are downstream of facts that only Discovery surfaces. Run it before committing to a platform shortlist or an integration approach.

Objectives:

  • Understand the commercial model, the channel mix, and where revenue actually flows today
  • Map the ERP and CRM landscape and the integration footprint, since these drive the timeline more than platform choice
  • Quantify account and pricing complexity, the part generic platforms model worst
  • Identify which capabilities and which customers should come first

Stakeholders to engage:

  • Commercial and sales leadership (the revenue owner)
  • Sales operations and service operations (who run quoting, attribution, and cases)
  • Key account managers (the voice of the largest, most complex customers)
  • Finance, accounts receivable, and credit (terms, PO, invoicing, credit policy)
  • IT and enterprise architects (system-of-record reality and integration constraints)
  • Procurement-facing customers where possible (the buyer's own requirements: punchout, EDI, portals)

Current-state assessment areas:

  • Existing channels and their order share: web, EDI, punchout, rep, phone and email
  • ERP and CRM systems and versions, and what each masters today
  • Pricing and contract complexity: number and structure of price lists, discount logic, contract terms
  • Account hierarchy and buyer organizational structures in the customer base
  • Integration inventory: what systems talk to what today, and how
  • Punchout and EDI requirements of the top customers (which protocols, which procurement platforms)
  • Payment terms, credit, and AR processes
  • Current self-service adoption and the specific pain points pushing volume to reps
  • Quote and CPQ process maturity, and where it lives today

Outputs of Discovery:

  • A draft system-of-record map, ratified later with enterprise architects
  • A capability gap analysis: for each B2B essential, native versus configure versus build
  • An integration inventory and a channel-and-journey map
  • Non-functional requirements (scale, integration latency, availability)
  • A prioritized roadmap with an MVP scope and a risk register

Exit criteria (readiness to move from Discovery to design):

  • A ratified system-of-record map
  • A prioritized capability roadmap with an agreed MVP and first-wave customers
  • The integration approach decided (managed iPaaS, dedicated service, or point-to-point)
  • The platform shortlist reduced to a real evaluation set

Personas and core journeys

Model the solution around the organization's roles, not a single shopper. These personas drive permissions, workflows, and the data model.

Persona Side What they need
Account / buyer administrator Buyer org Manage their own users, roles, ship-to locations, budgets, and approval rules (delegated administration)
Requisitioner Buyer org Build carts and requisitions against contract pricing; submit for approval
Approver Buyer org Review and approve or reject requisitions against budgets and spending limits
Accounts payable / finance Buyer org POs, invoices, statements, payment terms, tax exemption status
Sales representative Selling org Quote and order on behalf of accounts; negotiate; manage the opportunity
Customer service representative (CSR) Selling org Reorders, order changes, returns, claims, expedites, case handling
Sales operations / admin Selling org Price lists, catalogs, entitlements, account setup, commission attribution

Core journeys to specify with the BA team (each is a process flow with owners, systems touched, and exception paths):

  • Self-service reorder: returning buyer reorders from history, saved lists, or quick order by SKU
  • Requisition to approval: requisitioner builds an order, approval routes by amount, cost center, or budget, then converts to a PO
  • Request for quote to order (assisted): buyer or rep raises an RFQ, it is priced and negotiated, the quote is approved, and it converts to an order
  • Punchout requisition: buyer shops the catalog from inside their procurement system and returns the cart for approval and PO creation
  • Rep order on behalf of: a rep acts as an account, builds or modifies a cart, applies negotiated terms, and submits, with full audit
  • Service and returns: a CSR handles a reorder, a return or claim (RMA), an order change, or an expedite, against an existing order
  • New account onboarding: account creation, hierarchy setup, entitlement and price-list assignment, first order

Account model, entitlements, and pricing

This is the structural core of B2B and the part B2C platforms model poorly. Specify it explicitly before any UI work.

  1. Account hierarchy is a first-class entity. Model the organization tree: parent company, business units, divisions, and the distinct sold-to, bill-to, and ship-to relationships. Orders, pricing, entitlements, and reporting all roll up and down this tree. Decide where each attribute is mastered (commonly the ERP or CRM, not commerce).
  2. Roles and permissions are delegated. The buyer's own administrator manages their users and roles. The selling org defines the role model; the buyer operates it. Permissions govern who can see pricing, who can order, who must seek approval, and up to what value.
  3. Budgets and spending limits are enforced server-side. Approval routing keys off order value, cost center, and remaining budget. These are controls, not UI conveniences, and the enforcement lives in the service layer.
  4. Catalogs are entitled. A customer sees only the products they are contracted to buy, at the pricing they are contracted to pay. Entitlement is both a commercial rule and a security boundary (see Security below): a buyer must never be able to see or order outside their entitlement.
  5. Pricing is customer-specific and resolved by explicit rules. Contract price lists, volume and tier breaks, account-specific discounts, and promotions combine through a defined resolution order. Document that order, and define whether price is computed in the ERP and read by commerce, computed in commerce against synced data, or a hybrid. Never let two systems compute price by different logic.
  6. Tax handling reflects B2B reality. Resale and tax-exemption certificates, use tax, and multi-jurisdiction VAT are managed, with exemption status tied to the account and validated, not entered ad hoc at checkout.

Assisted and multi-touch selling

Enterprise B2B is blended commerce. The solution must let a sale move fluidly between self-service and people, sales and service, without losing context, control, or attribution. This is the capability that most generic platforms underserve, and the one this engagement centers on.

  1. Order and quote on behalf of, with audit. A rep or CSR can act as an account: build or modify a cart, apply negotiated pricing within their authority, and submit. Every such action is logged with the acting user, the account acted for, and the change made (this extends the audit-logging standard in Core Section 4). Impersonation is a privileged, time-bound, fully audited capability, never a shared login.
  2. The CRM is the rep's system of record. Reps work the account, opportunity, and quote in the CRM (commonly Salesforce or Dynamics). Commerce surfaces order and behavioral activity into the CRM, and quotes flow from CRM or CPQ into commerce as orders. Define this contract precisely so the rep is never reconciling two systems by hand.
  3. Shared carts and guided selling. A buyer can build a cart and hand it to a rep for help; a rep can build a cart and send it to the buyer to approve and submit. Guided selling and configuration assist the rep on complex products.
  4. Service workflows are first-class, not afterthoughts. CSRs handle reorders, order modifications, returns and claims (RMA), and expedites against existing orders, with case management integrated into the service platform. The CSR tools are a product surface with the same quality bar as the storefront, including accessibility.
  5. Handoffs preserve context. Self-service to assisted and back, and sales to service, must carry the cart, the account, the history, and the conversation. A unified customer timeline (fed through the CRM and a CDP) gives every toucher of the account the same view.
  6. Attribution is designed in. When an online order is influenced or placed by a rep, credit and commission attribution must be unambiguous. Decide the attribution rules with sales operations before launch; retrofitting them is contentious and error-prone.
  7. AI assist follows the AI Addendum. Drafting quotes, summarizing an account before a call, suggesting reorders, and assisting CSR responses are strong AI candidates and are governed by Section 16: classified by risk, eval-backed, cost-managed, and guardrailed, with a human approving any consequential action (consistent with the agentic human-in-the-loop standard).

Quote-to-cash and CPQ

The assisted motion runs on a quote-to-cash backbone. Specify it as a lifecycle, not a feature.

  1. RFQ intake. Buyers and reps raise quote requests from the catalog, from a configured product, or from a blank quote. Capture the requesting account, contact, and context.
  2. Configure, price, quote (CPQ). For configurable or engineered products, CPQ enforces valid configurations (rules, compatibility, bills of material), prices them against contract logic, and produces a quote. Decide whether CPQ lives in the commerce platform, the CRM, or a dedicated CPQ tool, and which system owns the pricing rules.
  3. Negotiation and versioning. Quotes support multi-round negotiation with versioned history and clear current-state. Approval routing applies on the selling side (discount thresholds) and the buying side (budget and authority).
  4. Quote to order. An approved quote converts to an order without re-keying, carrying its negotiated pricing and terms. The conversion is idempotent (Core Section 3) so a double submission never creates two orders.
  5. Terms, PO, and invoicing. B2B rarely ends at a card charge. Support purchase-order numbers, net terms (commonly Net 30 to Net 90), credit lines, and invoicing, with accounts-receivable handled in the ERP or a dedicated provider. Where instant credit at checkout is offered, embedded underwriting through a net-terms provider keeps the buyer in flow rather than redirecting them to a financing application. Card payments still follow the PCI posture in Core Section 4 and the B2C payment-page controls where cards are accepted online.

Commerce architecture principles (B2B)

These extend Core Section 3 and the B2C architecture section. The API-first, multi-tenant, stateless, idempotent, and feature-flag principles carry over without exception.

  1. System-of-record discipline is the first architectural decision. For every core entity (customer, account hierarchy, product, price, inventory, order, invoice), name exactly one system of record and make every other system a synchronized consumer. Most B2B failures trace back to two systems believing they own the same data.
  2. Commerce is an orchestrator across channels, not a monolith. One commerce core serves many channels: web storefront, rep and CSR portals, punchout, EDI, and mobile. Favor a headless or API-first core so a single set of pricing, entitlement, cart, and order services backs every channel, rather than reimplementing rules per channel.
  3. Decide real-time versus cached per data type, with explicit staleness rules. Contract pricing and available-to-promise inventory are often authoritative in the ERP. Define whether each is read live (correct but slower and coupled to ERP availability) or cached (fast but potentially stale), and define the customer-facing behavior when the live source is unavailable: show last-known with a caveat, or deliberately block the action. Do not let this be implicit.
  4. Entitlement and price resolution are a first-class shared service. The logic that decides what an account may see and what it pays is used by every channel and is a security boundary. Build it once, server-side, and call it everywhere.
  5. Order orchestration is idempotent and reconciled. Orders captured online, via punchout, or via EDI flow to the ERP through an orchestration layer that is idempotent, retries safely, dead-letters failures, and reconciles state. A lost or duplicated order is a customer-trust incident, not a backend curiosity.
  6. Degrade deliberately. A failing recommendation or review service must never block an order (per B2C). A failing pricing or ATP call requires an explicit, designed decision, not a stack trace shown to the buyer.

Integration architecture

Integration is where enterprise B2B engagements are won or lost, and it is the single largest driver of timeline and risk. Treat it as a primary workstream, not glue.

System-of-record map (define and ratify with the BA team and the client's enterprise architects):

Entity Typical system of record Integration pattern
Customer / account hierarchy CRM or ERP Sync to commerce; event-driven on change
Product / catalog PIM or ERP Batch plus event-driven to commerce and search
Price (contract, tier, promo) ERP (often) Live read or scheduled sync, per principle above
Inventory / available-to-promise ERP or WMS Live read or near-real-time sync
Order ERP (post-capture) Async, idempotent orchestration from commerce
Invoice / AR / credit ERP or AR provider Async; surfaced read-only in the portal
Opportunity / quote / case CRM or CPQ Bidirectional with commerce

Integration principles:

  • One system of record per entity, ratified and documented; no shared ownership
  • Contract-first integration: interfaces defined as versioned contracts (Core Section 3), not discovered at runtime
  • Asynchronous and event-driven by default; synchronous only where the user genuinely needs a live answer (live pricing, ATP at checkout)
  • Idempotency, retries with backoff, dead-letter queues, and a reconciliation process for every order and financial flow
  • Every integration flow is observable (Core Section 7): success rate, latency, and backlog are monitored and alerted, not assumed
  • An integration approach chosen deliberately: managed iPaaS, a dedicated integration service, or point-to-point, with the trade-off documented in an ADR

Procurement and EDI as integration surfaces:

  • Punchout supported via cXML and OCI, the two dominant protocols, covering the major procurement platforms (SAP Ariba, Coupa, Oracle, JAGGAER, and others). A managed punchout gateway is usually preferable to bespoke per-buyer integrations
  • EDI supported for the core order documents where buyers require it: purchase order (850), order acknowledgment (855), advance ship notice (856), and invoice (810)
  • Punchout and EDI order flows carry the same idempotency, reconciliation, and observability guarantees as the online order path, and are treated as ISV-grade integrations under Core Section 5 (rate-limit handling, retries, graceful degradation)

Identity and access

B2B identity is organizational and delegated, and it extends Core Section 4.

  • Buyer-organization SSO via SAML or OIDC federation, so a buyer's employees authenticate through their own identity provider
  • Delegated administration: the buyer's administrator provisions and deprovisions their own users and assigns roles within the bounds the selling org defines
  • Automated provisioning (for example SCIM) where buyer organizations require it
  • A role and permission model enforced server-side as a security boundary, never only in the UI; permissions gate catalog visibility, pricing visibility, ordering, and approval authority
  • Act-as / impersonation for reps and CSRs is privileged, scoped, time-bound, and fully audited (acting user, target account, actions taken)
  • Punchout session identity is validated and trusted per the protocol; punchout sessions are scoped to the correct account, entitlement, and pricing

Security, compliance, and data handling (B2B)

Extends Core Section 4 and the B2C security section. The consumer-PII surface is smaller; the commercial-confidentiality and integrity surface is larger.

  • Entitlement isolation is a hard security boundary. A buyer must never see another account's pricing, catalog, orders, or documents. Treat cross-account exposure with the same severity as cross-tenant data leakage in Core Section 3: it is a SEV 1 incident. Verify isolation in every pre-release security review.
  • Pricing and contract data are confidential. Negotiated price lists and contract terms are sensitive commercial data; protect them in transit, at rest, in logs, and in any data sent to AI features (per the AI Addendum's data-handling rules).
  • All assisted and impersonated actions are audited. Who did what, for which account, when, with before-and-after state, retained per the SOC 2 logging standard.
  • Tax-exemption and certificate data is handled and validated, tied to the account, with an audit trail.
  • AR, credit, and net-terms data carries financial-data obligations. Where a third-party net-terms or AR provider is used, vet it under the vendor-management program (Core Section 4) and document the data shared.
  • Card payments keep PCI scope minimal (Core Section 4 and the B2C payment-page controls). Note that PO, terms, and invoice flows shift much of the volume off card rails, which changes but does not remove the scope.
  • Accessibility (WCAG 2.2 AA) applies to every portal, including the rep and CSR tools, not only the public storefront (see the B2C tab for the legal landscape).
  • Data residency is configurable where multinational buyers require it.

Platform selection (B2B)

There is no single correct B2B platform; there is a correct one for the client's ERP and CRM ecosystem, account and pricing complexity, channel mix, and team. The integration footprint, not the platform's feature list, is the dominant cost and timeline driver. Record the choice as a Level 3 decision under the core governance framework.

Selection categories and current examples:

  • B2B-native: OroCommerce (open source; bundles commerce, CRM, CPQ, and ERP connectors on one data layer, which fits the single-system argument and the core open-source preference) and Virto Commerce (open source, .NET, composable). Strong when deep B2B procurement logic is the core requirement.
  • ERP-native: SAP Commerce Cloud (for SAP estates), Sana Commerce (strong for Microsoft Dynamics), Oracle / NetSuite SuiteCommerce. Strong when the ERP runs most business logic and real-time ERP connectivity is paramount.
  • CRM-native: Salesforce B2B Commerce. Strong when Salesforce is the system of record and the assisted motion lives in the CRM.
  • Enterprise-customizable: Adobe Commerce. Broad native B2B features and a wide connector ecosystem, at a high development and operating cost.
  • Composable: commercetools, Elastic Path, Spryker. Maximum flexibility to serve many channels from one core, requiring a capable engineering team and the highest long-term ownership burden, since native B2B workflows must be assembled.
  • Mid-market and blended: BigCommerce B2B Edition, and Shopify Plus B2B where a unified B2B and B2C motion and speed to value outweigh deep complexity.
  • B2B layer on an existing store: a B2B overlay (for example SparkLayer) where the client already runs a storefront and wants account pricing, portals, and rep ordering without replatforming.

Selection checklist:

  • Native depth assessed for each B2B essential: account hierarchy, delegated roles, entitled catalogs, contract pricing, quote/CPQ, punchout, EDI, and assisted selling. For each, decide native, configure, or build
  • ERP and CRM connector fit assessed against the client's actual systems and versions, since this drives the timeline
  • Three-year total cost of ownership modeled, including license, implementation, integration, and operations
  • Exit cost and data portability assessed; vendor lock-in named explicitly
  • Channel coverage confirmed: can one commerce core serve web, rep portal, punchout, and EDI without per-channel reimplementation

Extends Core Section 13 and differs sharply from B2C: success is measured in digital adoption, order accuracy, integration health, and account retention, not session conversion. Reviewed with the business and sales operations.

  • Digital order share: percentage of orders placed self-service versus assisted, trended (the core transformation metric)
  • Reorder rate and quick-order usage

  • Quote-to-order conversion rate and quote cycle time
  • Requisition approval cycle time

  • Punchout and EDI order success rate

  • Net revenue retention and account retention (B2B is relationship-driven; retention outweighs acquisition)
